# 성능

아래 수치는 모두 2026-10-20~21에 직접 측정한 값입니다. 측정 환경이 다르면 결과도 달라집니다.

## 측정 환경

- Windows 11 Home (10.0.26200), 논리 CPU 8개
- Node 24.19.0 (수학 엔진 벤치마크)
- Microsoft Edge 155.0.4283.62 **헤드리스**(puppeteer-core). 헤드리스 브라우저는 실제 화면 출력과 GPU 래스터 비용이 일반 창과 다를 수 있으므로, FPS는 상한 60에 묶인 참고값입니다.
- 이전 버전과의 비교는 첫 릴리스(커밋 `10e5bad`)를 별도 폴더에 빌드해 **같은 스크립트·같은 브라우저·같은 뷰포트(1440×900)**로 측정했습니다(`node e2e/perf.mjs --dist <dir>`).

## 수학 엔진 (`npm run bench`)

UI 개편 전후로 수학 엔진 코드는 바뀌지 않았습니다. 하트 예제 기준, 한 번 실행 시간의 평균입니다.

| N | FFT | 참조 DFT | 재표본화 + 스펙트럼 + 정렬 2회 | K = N−1 선택 + 궤적(역 FFT) | 에피사이클 1회 평가(K = N−1) |
|---|---|---|---|---|---|
| 256 | 0.007 ms | 1.25 ms | 0.10 ms | 0.09 ms | 7.5 µs |
| 512 | 0.013 ms | 4.84 ms | 0.14 ms | 0.08 ms | 14.7 µs |
| 1024 | 0.026 ms | 20.13 ms | 0.32 ms | 0.14 ms | 34.7 µs |
| 2048 | 0.059 ms | – | 0.67 ms | 0.33 ms | 73.1 µs |

N = 1024일 때 FFT는 참조 DFT보다 약 770배 빠릅니다. 입력이 바뀔 때 다시 계산하는 전체 분석도 1ms 미만이므로 Web Worker는 도입하지 않았습니다.

## 레이아웃: 애니메이션 캔버스 크기 (이전 → 현재)

같은 헤드리스 Edge, 첫 방문(하트 예제) 직후의 CSS px입니다.

| 뷰포트 | 이전 캔버스 | 현재 캔버스 | 현재 캔버스가 첫 화면에 전부 보임 | 재생 버튼·원 개수 슬라이더가 첫 화면 안 |
|---|---|---|---|---|
| 데스크톱 1440×900 | 986×574 (566k px²) | 1391×598 (832k px²), **+47%** | 이전 ○ → 현재 ○ | 이전 ○ → 현재 ○ |
| 모바일 390×844 | 330×538 (178k px²), 화면 아래 y = 878부터 시작 | 364×447 (163k px²), y = 65부터 | **이전 ✕ → 현재 ○** | **이전 ✕(재생 버튼 y = 1477, 슬라이더 y = 1653) → 현재 ○(y = 586 / 733)** |
| 모바일 360×800 | 300×510 (153k px²), y = 848부터 | 334×403 (135k px²), y = 65부터 | **이전 ✕ → 현재 ○** | **이전 ✕ → 현재 ○** |

- 데스크톱에서는 캔버스 폭이 약 41%, 면적이 약 47% 늘었습니다. 높이는 기본 구성에서 거의 같고(574 → 598px), 대신 왼쪽 고정 패널이 사라져 폭을 모두 씁니다.
- 모바일에서는 캔버스 **면적 자체는 이전보다 약 8~12% 작습니다.** 이전에는 캔버스를 보려면 그림 입력 패널 아래까지 약 880px을 스크롤해야 했고, 재생 버튼과 슬라이더는 그보다 더 아래(y ≈ 1480~1650)에 있었습니다. 현재는 캔버스와 핵심 컨트롤이 스크롤 없이 한 화면에 있습니다. 컨트롤(터치 대상 44px)을 확보하기 위해 면적을 일부 양보했습니다.

## 브라우저 렌더링 (`npm run perf`)

1440×900 뷰포트, DPR 1, 하트 예제, 기본 표시 설정(원·벡터·궤적·원본). 각 행은 3초 동안 재생하며 측정했습니다.

- **draw**: 동적 레이어를 그리는 JavaScript 호출 시간의 평균(CPU 측 명령 제출 시간이며 GPU 래스터 시간은 포함하지 않음)
- **새 K → 표시**: 원 개수 입력 후 Enter부터 두 번째 animation frame까지. 측정 방식 때문에 rAF 대기 약 17–33ms가 포함되며, 한 번 측정한 값이라 ±15ms 정도의 편차가 있습니다.
- **슬라이더 입력**: 슬라이더 `input` 이벤트 한 번을 보낸 뒤 React 갱신이 끝날 때까지의 동기 시간

- "새 K → 표시"와 슬라이더 입력의 이전/현재 차이는 대부분 측정 편차 범위입니다(이전 2048/K = 100의 122.6ms는 한 번 튄 값으로 보이며 원인은 확인하지 않았습니다). 개편으로 원 개수 응답이 빨라졌다고 주장하지 않으며, **느려지지도 않았다**는 것만 확인했습니다.
- 원 개수 변경은 재시작(`player.restart()`)을 포함하는데도 이전보다 느리지 않았습니다. 재시작은 시간 값 하나를 0으로 돌리는 일이고, 새 계수 선택·궤적 계산은 이전과 같은 경로입니다.

### 드로어와 유휴 상태 (현재 버전)

| 항목 | 결과 |
|---|---|
| 드로어 열기 → 두 프레임 그려짐 | 중앙값 30.4 ms (5회: 24.0 ~ 30.6 ms) |
| 드로어 닫기 → 두 프레임 그려짐 | 중앙값 26.2 ms (5회: 23.1 ~ 28.7 ms) |
| 5회 열고 닫는 동안 FFT 실행 | **0회** |
| CPU 4배 감속에서 드로어 열기 / 닫기 | 중앙값 29.7 / 27.0 ms (5회: 20.8~40.9 / 23.8~35.2 ms) |

두 프레임 대기(약 33ms)가 포함된 값이므로 사실상 한두 프레임 안에 열리고 닫힙니다.

| 상태 | 메인 스레드 사용률 | 스크립트 실행 비율 (이전 → 현재) |
|---|---|---|
| 재생 중 (K = 100, 3초 평균) | 이전 15.2% → 현재 12.8% | 4.0% → 2.2% |
| 일시정지 (3초 평균) | 이전 0.1% → 현재 0.1% | 0.0% → 0.0% |

메인 스레드 사용률은 CDP `Performance.getMetrics`의 `TaskDuration` 증가량을 경과 시간으로 나눈 값입니다. 일시정지하면 rAF 루프가 멈추므로 사실상 유휴 상태이고, 드로어를 열어 두기만 해도 계산이 일어나지 않습니다.

## 적용한 최적화와 그 효과

1. **FFT는 입력이 바뀔 때만** 다시 계산합니다. K나 선택 방식을 바꾸거나, 드로어를 열고 닫거나, 그림을 그리는 동안에는 실행되지 않습니다(`counters.spectrum`을 브라우저 테스트가 확인).
2. **궤적은 영 패딩 역 FFT로 한 번에** 계산합니다. 매 프레임에는 배열을 잘라 그리기만 하고, 펜 끝만 정확히 평가합니다.
3. **정적/동적 레이어를 분리**했습니다. 매 프레임에는 동적 레이어만 다시 그립니다.
4. **원은 화면상 크기별로 4단계로 묶어 일괄** 그리고, 0.6px 미만인 원은 생략합니다.
5. **재생 중에는 React 재렌더링이 없습니다.** 타임라인·시간 표시는 ref로 직접 갱신합니다. 정지하면 rAF 루프가 없습니다.
6. **차트는 분석 패널을 열었을 때만** 그리고, 열려 있어도 `memo` + `useDeferredValue`로 슬라이더보다 낮은 우선순위로 갱신합니다. 첫 릴리스에서 이 지연을 적용하기 전에는 원 개수 슬라이더 입력부터 React 동기 커밋까지가 13~34ms였고, 적용 후 1.5~3.6ms였습니다(첫 릴리스 측정값).
7. **드로어는 마운트된 채 숨깁니다**(`visibility: hidden` + `inert`). 열고 닫을 때 컴포넌트를 새로 만들거나 캔버스를 다시 초기화하지 않으므로 위 표처럼 지연이 짧습니다.

## 측정하지 않은 것

- 실제 모바일 기기와 일반(비헤드리스) 창에서의 FPS
- 고해상도(DPR 2~3) 대형 화면에서의 GPU 래스터 비용
- 모바일 뷰포트에서의 FPS와 터치 입력 지연(이번 측정은 데스크톱 1440×900만)
