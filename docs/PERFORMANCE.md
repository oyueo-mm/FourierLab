# 성능

아래 수치는 모두 2026-10-20에 직접 측정한 값입니다. 측정 환경이 다르면 결과도 달라집니다.

## 측정 환경

- Windows 11 Home (10.0.26200), 논리 CPU 8개
- Node 24.19.0 (수학 엔진 벤치마크)
- Microsoft Edge 155.0.4283.62 **헤드리스**(puppeteer-core). 헤드리스 브라우저는 실제 화면 출력과 GPU 래스터 비용이 일반 창과 다를 수 있으므로, FPS는 상한 60에 묶인 참고값입니다.

## 수학 엔진 (`npm run bench`)

하트 예제 기준, 한 번 실행 시간의 평균입니다.

| N | FFT | 참조 DFT | 재표본화 + 스펙트럼 + 정렬 2회 | K = N−1 선택 + 궤적(역 FFT) | 에피사이클 1회 평가(K = N−1) |
|---|---|---|---|---|---|
| 256 | 0.007 ms | 1.25 ms | 0.10 ms | 0.09 ms | 7.5 µs |
| 512 | 0.013 ms | 4.84 ms | 0.14 ms | 0.08 ms | 14.7 µs |
| 1024 | 0.026 ms | 20.13 ms | 0.32 ms | 0.14 ms | 34.7 µs |
| 2048 | 0.059 ms | – | 0.67 ms | 0.33 ms | 73.1 µs |

N = 1024일 때 FFT는 참조 DFT보다 약 770배 빠릅니다. 입력이 바뀔 때 다시 계산하는 전체 분석도 1ms 미만이므로 Web Worker는 도입하지 않았습니다.

## 브라우저 렌더링 (`npm run perf`)

1440×1000 뷰포트, DPR 1, 시각화 캔버스 986×638 CSS px, 하트 예제, 기본 표시 설정(원·벡터·궤적·원본). 각 행은 3초 동안 재생하며 측정했습니다.

- **draw**: 동적 레이어를 그리는 JavaScript 호출 시간의 평균(CPU 측 명령 제출 시간이며 GPU 래스터 시간은 포함하지 않음)

## 적용한 최적화와 그 효과

1. **FFT는 입력이 바뀔 때만** 다시 계산합니다. K나 선택 방식을 바꾸면 기존 계수를 재사용합니다(`useAnalysis`의 단계별 메모이제이션).
2. **궤적은 영 패딩 역 FFT로 한 번에** 계산합니다. 매 프레임에는 배열을 잘라 그리기만 하고, 펜 끝만 정확히 평가합니다.
3. **정적/동적 레이어를 분리**했습니다. 매 프레임에는 동적 레이어만 다시 그립니다.
4. **원은 화면상 크기별로 4단계로 묶어 일괄** 그리고, 0.6px 미만인 원은 생략합니다.
5. **재생 중에는 React 재렌더링이 없습니다.** 타임라인·시간 표시는 ref로 직접 갱신합니다. 정지하면 rAF 루프가 없습니다.
6. **차트 갱신 지연**(`memo` + `useDeferredValue`): 원 개수 슬라이더 입력부터 React 동기 커밋까지의 시간을 측정한 결과입니다.

   | 열린 분석 탭 | 적용 전 | 적용 후 |
   |---|---|---|
   | 주파수 스펙트럼 | 20–34 ms | 1.5–2.3 ms |
   | 원 개수와 오차 | 13–27 ms | 1.5–2.4 ms |
   | 수학 원리 | 1.2–2.6 ms | 1.7–3.6 ms |

   이 최적화 전에는 K 변경부터 화면 표시까지(위 표의 방식) 52–71ms였습니다.

## 측정하지 않은 것

- 실제 모바일 기기와 일반(비헤드리스) 창에서의 FPS
- 고해상도(DPR 2–3) 대형 화면에서의 GPU 래스터 비용
